# PR: Write-Ahead Log (WAL) с батчингом и сегментированием

# TL;DR
1. Конфигурация WAL — добавить секцию wal в YAML-конфиг (enabled, data_directory, segment_max_size, batch_max_size, batch_timeout). По умолчанию WAL отключён.
2. Формат записи и сериализация — бинарный формат entry: [CRC32][LSN][длина][данные]. LSN — глобальный монотонный счётчик записей. Данные содержат тип команды (SET/DEL), ключ и значение. Пакет internal/wal/entry/.
3. Сегмент WAL — обёртка над файлом: WriteBatch (write + fsync), ReadAll для восстановления, IsFull для ротации. Пакет internal/wal/segment/.
4. WAL-менеджер с батчингом — основная логика: клиент вызывает Write(entry), блокируется на канале done. Flush батча происходит по лимиту размера или таймауту.
Все клиенты одного батча разблокируются одновременно. Ротация сегментов при переполнении.
5. Восстановление при старте — сканируем WAL-директорию, сортируем сегменты по номеру, проигрываем все операции в engine последовательно.
6. Интеграция в Storage — перед записью в engine делаем wal.Write(...). При ошибке WAL — не пишем в engine. GET не затрагивает WAL.
7. Интеграция в cmd/server — инициализация WAL, восстановление при старте, graceful shutdown с flush оставшегося батча.
8. Тесты — unit-тесты entry/segment/WAL, интеграционные тесты (SET → рестарт → восстановление → GET), конкурентные тесты.
9. Моки — добавить WAL-интерфейс в generate.go для тестирования storage без реального WAL.

## Цель

Реализовать Write-Ahead Log для in-memory базы данных, чтобы модифицирующие операции (SET/DEL) записывались на диск **до** применения к движку. Это позволит восстанавливать данные после рестарта.

Ключевые требования:
- Запись операций батчами (не по одной), с flush по лимиту размера батча или таймауту.
- Клиент получает ответ **только после** того, как его операция записана в WAL и применена к движку.
- После `write` вызывается `fsync` для гарантии попадания данных на диск.
- WAL-файлы сегментируются: при достижении лимита размера текущий файл закрывается, создаётся новый.
- При старте БД — восстановление состояния из всех сегментов WAL (от старого к новому).
- По умолчанию WAL **отключён**; включается через конфигурацию.

## План действий

### Шаг 1. Конфигурация WAL

**Что делаем:** добавляем секцию `wal` в `Config` (`internal/config/app/config.go`).

**Новые поля:**

```yaml
wal:
  enabled: true              # включён ли WAL (default: false)
  data_directory: "./data/wal" # путь к директории WAL-файлов (default: "./data/wal")
```

**Детали реализации:**
- Добавить структуру `WALConfig` в `config.go` и поле `WAL WALConfig` в `Config`.

- `segment_max_size` парсится через существующий `ParseMessageSize()`.
- `batch_timeout` парсится через `time.ParseDuration()`.
- Обновить `applyDefaults()` и `parseDerivedValues()`.

**Файлы:** `internal/config/app/config.go`, тесты конфигурации.

### Шаг 2. Формат записи WAL и сериализация

**Что делаем:** определяем бинарный формат записи (entry) WAL-файла и пишем сериализацию/десериализацию.

**Формат одной записи (entry):**

```
[CRC32 — 4 байта][LSN — 8 байт][Длина данных — 4 байта][Данные — N байт]
```

- **CRC32** — контрольная сумма от `[LSN][Длина данных][Данные]`. Позволяет при восстановлении обнаружить повреждённые записи.
- **LSN (Log Sequence Number)** — глобальный монотонно возрастающий `int64`. Каждая запись в WAL получает уникальный LSN. Генерируется через `atomic.AddInt64`. LSN не сбрасывается при ротации сегмента — он глобален для всего WAL.

Данные внутри entry — это закодированная операция:
- Тип команды: `SET` или `DEL` (1 байт: `0x01` = SET, `0x02` = DEL).
- Для SET: `[command_byte][key_len (4 bytes)][key][value_len (4 bytes)][value]`.
- Для DEL: `[command_byte][key_len (4 bytes)][key]`.

**Зачем LSN:**
- Уникальная идентификация каждой записи в логе.
- При восстановлении можно определить последний успешно записанный LSN и продолжить нумерацию.
- Основа для будущих возможностей: репликация, checkpoint'ы, point-in-time recovery.

**Детали реализации:**
- Пакет `internal/wal/entry/` — структура `Entry{LSN, CommandType, Key, Value}` + методы `Encode() []byte`, `Decode([]byte) (Entry, error)`.
- LSN-генератор — отдельная структура с `atomic.AddInt64`, аналогично существующему `IDGenerator` в storage.
- CRC32 из стандартной библиотеки (`hash/crc32`).
- Тесты: кодирование/декодирование round-trip, битый CRC → ошибка, монотонность LSN.

**Файлы:** `internal/wal/entry/entry.go`, `internal/wal/entry/tests/entry_test.go`.

### Шаг 3. Сегмент WAL (работа с файлом)

**Что делаем:** реализуем один WAL-сегмент — обёртку над файлом с возможностью записи batch-а записей и чтения для восстановления.

**Интерфейс сегмента:**

```go
type Segment struct {
    file        *os.File
    currentSize int64
    maxSize     int64
}

func NewSegment(path string, maxSize int64) (*Segment, error)
func (s *Segment) WriteBatch(entries []entry.Entry) error  // write + fsync
func (s *Segment) ReadAll() ([]entry.Entry, error)         // чтение всех записей
func (s *Segment) IsFull() bool                            // currentSize >= maxSize
func (s *Segment) Close() error
```

**Детали реализации:**
- `WriteBatch`: сериализует все entries в буфер, делает один `Write` + `Sync()` (fsync). Обновляет `currentSize`.
- `ReadAll`: читает файл последовательно, декодирует entries. Пропускает записи с битым CRC (логирует предупреждение).
- Именование файлов: `wal_000001.log`, `wal_000002.log`, ... (нумерация по порядку).
- При создании нового сегмента — создаёт файл с `os.O_CREATE|os.O_WRONLY|os.O_APPEND`.

**Файлы:** `internal/wal/segment/segment.go`, `internal/wal/segment/tests/segment_test.go`.

### Шаг 4. WAL-менеджер (батчинг + сегментирование)

**Что делаем:** реализуем основной WAL-менеджер, который собирает батчи операций, пишет их на диск и управляет ротацией сегментов.

**Интерфейс:**

```go
type WAL struct {
    cfg             config.WALConfig
    currentSegment  *segment.Segment
    segmentCounter  int
    lsnCounter      int64          // глобальный LSN-счётчик (atomic)
    mu              sync.Mutex
    batch           []batchItem
    flushTimer      *time.Timer
    logger          *zap.Logger
}

type batchItem struct {
    entry  entry.Entry
    done   chan error   // канал, через который клиент ждёт результат записи
}

func NewWAL(cfg config.WALConfig, logger *zap.Logger) (*WAL, error)
func (w *WAL) Write(commandType byte, key, value string) error  // блокирующий; LSN назначается внутри
func (w *WAL) Recover(engine Engine) error                       // восстановление + установка lsnCounter
func (w *WAL) Close() error                                      // flush оставшегося батча + закрытие
```

**Механизм батчинга (ключевая логика):**

1. Клиент вызывает `Write(commandType, key, value)` — WAL назначает следующий LSN через `atomic.AddInt64`, создаёт entry, добавляет в `batch`, клиенту возвращается канал `done`.
2. Клиент блокируется на `<-done` (ждёт, пока батч запишется).
3. Flush батча происходит при одном из условий:
   - `len(batch) >= batchMaxSize` — батч заполнен.
   - Сработал `batchTimeout` таймер — прошло слишком много времени с первой записи в текущем батче.
4. При flush:
   - Берём текущий батч целиком под мьютексом, создаём новый пустой батч.
   - Проверяем, не переполнен ли текущий сегмент → если да, создаём новый.
   - Вызываем `segment.WriteBatch(entries)`.
   - Рассылаем результат (nil или error) во все `done`-каналы клиентов из этого батча.
5. Все клиенты из батча разблокируются одновременно.

**Ротация сегментов:**
- Перед записью батча проверяем: если `currentSegment.IsFull()` → `Close()` текущий, создаём новый с инкрементированным номером.

**Файлы:** `internal/wal/wal.go`, `internal/wal/tests/wal_test.go`.

### Шаг 5. Восстановление при старте

**Что делаем:** при запуске БД читаем все WAL-сегменты по порядку и проигрываем операции в движок.

**Алгоритм:**
1. Сканируем `data_directory` на наличие файлов `wal_XXXXXX.log`.
2. Сортируем по номеру (от старого к новому).
3. Для каждого сегмента вызываем `ReadAll()` и последовательно применяем:
   - SET → `engine.Set(ctx, key, value)`
   - DEL → `engine.Del(ctx, key)`
4. Запоминаем максимальный LSN из всех прочитанных записей.
5. Устанавливаем `lsnCounter = maxLSN`, чтобы новые записи продолжили нумерацию.
6. После восстановления создаём новый сегмент для записи (с номером = последний + 1).

**Обработка ошибок:**
- Если CRC записи не совпадает — пропускаем запись, логируем warning.
- Если файл сегмента повреждён полностью — логируем error, продолжаем с следующими сегментами.

**Файлы:** логика в `internal/wal/wal.go` (метод `Recover`), тесты в `internal/wal/tests/`.

### Шаг 6. Интеграция WAL в Storage-слой

**Что делаем:** встраиваем WAL между получением запроса и записью в движок.

**Текущий flow (без WAL):**
```
Storage.Set(ctx, key, value) → engine.Set(ctx, key, value)
```

**Новый flow (с WAL):**
```
Storage.Set(ctx, key, value) →
  1. wal.Write(Entry{SET, key, value})   // блокируется до записи батча на диск
  2. engine.Set(ctx, key, value)          // записываем в память
  3. return nil                           // отвечаем клиенту
```

**Детали реализации:**
- В конструктор `storage` добавить опциональную зависимость `WAL` (может быть nil, если WAL отключён).
- Методы `Set` и `Del` — перед вызовом engine делают `wal.Write(...)`, если WAL включён.
- `Get` — WAL не затрагивает (только чтение из engine).
- При ошибке записи WAL — возвращаем ошибку клиенту, **не** пишем в engine.

**Файлы:** `internal/database/storage/storage.go`, `internal/database/storage/engine.go` (если нужен новый интерфейс для WAL).

### Шаг 7. Интеграция в точку входа (cmd/server)

**Что делаем:** при старте сервера — инициализируем WAL (если включён в конфиге), выполняем восстановление, передаём в storage.

**Порядок инициализации:**
1. Загрузить конфиг.
2. Создать engine.
3. **Если WAL включён:**
   - `wal.NewWAL(cfg.WAL, logger)`.
   - `wal.Recover(engine)` — восстановить состояние из сегментов.
4. Создать storage (с WAL или без).
5. Создать database, запустить сервер.

**При остановке (graceful shutdown):**
- Вызвать `wal.Close()` — flush оставшегося батча, закрытие файлов.

**Файлы:** `cmd/server/main.go`, `cmd/cli/main.go` (если CLI тоже поддерживает WAL).

**Unit-тесты:**
- `entry`: кодирование/декодирование, битый CRC, пустые поля, большие значения.

**Интеграционные тесты:**
- Storage + WAL + Engine: полный цикл SET/GET/DEL → перезапуск → восстановление → проверка данных.
- Конкурентная запись: несколько горутин пишут одновременно, все записи корректно попадают в WAL.

**Тесты конфигурации:**

## Критерии готовности (Definition of Done)

- WAL записывает модифицирующие операции (SET/DEL) батчами на диск с fsync.
- Клиент блокируется до завершения записи батча в WAL.
- Flush батча срабатывает по размеру или таймауту.
- WAL-файлы сегментируются при достижении лимита размера.
- При рестарте БД состояние полностью восстанавливается из WAL-сегментов.
- WAL отключён по умолчанию; включается через YAML-конфиг.
- Тесты покрывают entry, segment, WAL-менеджер, интеграцию со storage.
- `go test -race ./...` проходит.

## Риски и меры

- **Риск:** гонки при конкурентном доступе к batch/сегменту.
  - Мера: мьютекс в WAL-менеджере, `go test -race`.
- **Риск:** потеря данных при аварийном завершении между write и fsync.
  - Мера: fsync после каждого WriteBatch; CRC для обнаружения повреждений при восстановлении.
- **Риск:** большой таймаут батча → долгое ожидание клиентов.
  - Мера: дефолт `10ms`, настраиваемый через конфиг.
- **Риск:** слишком много мелких сегментов на диске.
  - Мера: разумный дефолт `segment_max_size = 16MB`.
